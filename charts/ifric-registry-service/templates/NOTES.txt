{{ include "ifric-registry-service.fullname" . }} has been deployed.

WHAT HAPPENS NOW
  1. The backend Pod runs two initContainers before the app starts:
     wait-for-postgres, then migrate (npm run migration:run).
{{- if .Values.keycloak.bootstrap.enabled }}
  2. The keycloak-bootstrap Job creates the realm '{{ .Values.env.keycloak.realm | default "ifric" }}', the
     'ifric' and '{{ .Values.env.keycloak.adminClientId }}' clients, the company_ifric_id/user_id
     protocol mappers, and the manage-users grant. The backend may log
     Keycloak errors until it finishes — that is expected, and it recovers
     on its own without a restart.
{{- else }}
  2. keycloak.bootstrap.enabled=false — NOTHING configures Keycloak for you.
     The backend will crash-loop on its fail-fast env check until you create
     the realm/clients/mappers yourself and supply both client secrets. See
     docs/keycloak-setup.md, then:

       helm upgrade {{ .Release.Name }} <chart> --reuse-values \
         --set secrets.keycloakClientSecret=<ifric secret> \
         --set secrets.keycloakAdminClientSecret=<ifric-admin secret>
{{- end }}
{{- if .Values.seed.enabled }}
  3. The seed Job POSTs /script once the backend answers, creating the
     default access groups and company categories. It runs on install only.
{{- if .Values.icid.enabled }}
  4. The icid-seed Job POSTs the bundled ICID's own /script, creating its
     dataspace/region/country/object-type taxonomy. Company creation fails
     without it: env.companyDefaultCode ({{ .Values.env.companyDefaultCode }}) is checked
     against those object types. Safe to re-run, so it also runs on upgrade.
{{- end }}
{{- end }}

Watch it come up:

  kubectl get pods -l app.kubernetes.io/instance={{ .Release.Name }}
{{- if .Values.keycloak.bootstrap.enabled }}
  kubectl logs job/{{ include "ifric-registry-service.fullname" . }}-keycloak-bootstrap
{{- end }}
{{- if .Values.seed.enabled }}
  kubectl logs job/{{ include "ifric-registry-service.fullname" . }}-seed
{{- end }}

REACH THE API

  kubectl port-forward svc/{{ include "ifric-registry-service.fullname" . }}-backend {{ .Values.service.port }}:{{ .Values.service.port }}
  curl http://localhost:{{ .Values.service.port }}/api-docs

{{- if not .Values.seed.enabled }}

SEED DATA (seed.enabled=false)
  A fresh database has no AccessGroup rows, so createCompany has no 'admin'
  group to assign and every permission check fails. Seed it once:

    kubectl exec deploy/{{ include "ifric-registry-service.fullname" . }}-backend -- \
      node -e "fetch('http://localhost:{{ .Values.service.port }}/script',{method:'POST'}).then(r=>r.text()).then(console.log)"

  Run it ONCE — /script inserts unconditionally, so a second run duplicates
  every access group and category.
{{- end }}

{{- if .Values.icid.enabled }}

ICID
  Bundled in this release, with its own MongoDB.
{{- if .Values.seed.enabled }}
  Its taxonomy is seeded automatically by the icid-seed Job — check it with:

    kubectl logs job/{{ include "ifric-registry-service.fullname" . }}-icid-seed

  If that Job timed out waiting for ICID, seed it by hand (safe to re-run):
{{- else }}
  seed.enabled=false, so its taxonomy is NOT seeded. Company creation will
  fail until you do it — env.companyDefaultCode ({{ .Values.env.companyDefaultCode }}) is checked
  against ICID's object types. Safe to re-run:
{{- end }}

    kubectl port-forward svc/{{ include "ifric-registry-service.icidHost" . }} {{ .Values.icid.service.port }}:{{ .Values.icid.service.port }}
    curl -X POST http://localhost:{{ .Values.icid.service.port }}/script
{{- else }}

ICID
  NOT enabled (icid.enabled=false). Company creation and certificates need
  env.icidServiceBackendUrl pointed at a reachable instance — they fail at
  call time, not at boot. Users, access groups, assets, twins, factories and
  product tagging all work without it.
{{- end }}
